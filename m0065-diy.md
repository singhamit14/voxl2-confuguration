## 1. The image is NOT standalone — load address 0x08001C00

```
initial SP    = 0x20005000     top of 20 KB SRAM -> STM32F103C8 confirmed
reset handler = 0x08005131
```

**The image is linked at `0x08001C00`**, so ModalAI's bootloader owns the first **7 KB**
(`0x08000000`–`0x08001BFF`). That bootloader is **not publicly distributed**.

> Do **not** infer the base from `reset & ~0xFFF` — the reset handler can sit anywhere in the
> image, and that shortcut gives a wrong answer (0x08005000) that hard-faults on boot.
>
> Derive it instead: vector entries 2–6 are `0x080049C5..D5`, *below* any wrong guess of
> 0x08005000, which is impossible. Scoring candidate bases by how many embedded string pointers
> resolve inside the image gives `0x08001C00` decisively. It is confirmed three ways: the reset
> handler there is a textbook `.data` copy / `.bss` zero / `bl main` startup; the default handlers
> at `0x080049C8+` are `e7fe` (`b .`) loops; and the literal `0x08001C00` appears in the image.

You do not need it to *run* the app — only to update firmware over UART. Flash with SWD and
place a small stub at `0x08000000` that sets `VTOR` and jumps:

```c
/* linked at 0x08000000, keeps flash below 0x08005000 occupied */
#define APP 0x08001C00u
__attribute__((naked, section(".isr_vector"))) void boot(void) {
    __asm volatile(
        "ldr r0, =0xE000ED08\n"   /* SCB->VTOR         */
        "ldr r1, =0x08001C00\n"
        "str r1, [r0]\n"
        "ldr r0, [r1]\n"          /* initial SP        */
        "mov sp, r0\n"
        "ldr r0, [r1, #4]\n"      /* reset handler     */
        "bx  r0\n");
}
```

Trade-off: you lose UART firmware update, which is fine because you are flashing over SWD.

**Verified working on hardware**: after flashing stub + app, `VTOR = 0x08001c00`, PC runs inside
the application, `VECTACT = 0` (thread mode) and `CFSR = 0` (no faults).

## 2. PWM pinout — CONFIRMED

Two 8-entry tables at **file offset 0x3FB0 / address 0x08005BB0** (GPIO bases) and **0x3FD0 /
0x08005BD0** (pin descriptors). The code loads `0x08005BB0` directly, which under the correct
base resolves to file offset 0x3FB0 — an independent confirmation of both the base and the table:

| # | GPIO base | descriptor | Pin | Timer / channel |
|---|---|---|---|---|
| 0 | GPIOA | `0x00000101` | **PA0** | TIM2_CH1 |
| 1 | GPIOA | `0x00000202` | **PA1** | TIM2_CH2 |
| 2 | GPIOB | `0x04010001` | **PB8** | TIM4_CH3 |
| 3 | GPIOB | `0x04020002` | **PB9** | TIM4_CH4 |
| 4 | GPIOA | `0x00004040` | **PA6** | TIM3_CH1 |
| 5 | GPIOA | `0x00008080` | **PA7** | TIM3_CH2 |
| 6 | GPIOB | `0x00000101` | **PB0** | TIM3_CH3 |
| 7 | GPIOB | `0x00000202` | **PB1** | TIM3_CH4 |

Descriptor encoding, read off the config loop at `0x080042D0`:

- bits `[7:0]` — lowest set bit gives the 4-bit field index within the control register
- bits `[15:8]` — pin mask, used for the `ODR` write
- bits `[31:24]` — control register offset: `0x00` = `CRL` (pins 0–7), `0x04` = `CRH` (pins 8–15)

Each pin is configured as **alternate-function push-pull**. The static table writes `0x9`
(AF_PP, 10 MHz); the live chip reads back `0xB` (AF_PP, 50 MHz), so a later pass raises the slew
rate. Both are AF push-pull — only the edge rate differs.

### Confirmed on live silicon

After flashing, read back with the core halted:

```
GPIOA_CRL = bb4444bb    PA0=B PA1=B  PA2..PA5=4  PA6=B PA7=B
GPIOB_CRL = 444844bb    PB0=B PB1=B
GPIOB_CRH = 664444bb    PB8=B PB9=B
TIM2/3/4  PSC=2 ARR=59999
```

Exactly those eight pins are alternate-function and **no others** — every other GPIO reads `4`
(floating input), `8` or `6`. PA13/PA14/PA15 read `8`: SWD survives, as predicted.

**Cross-check:** the output-compare init calls at `0x080043D8`–`0x08004428` run in the order
TIM2_CH1, TIM2_CH2, TIM4_CH3, TIM4_CH4, TIM3_CH1, TIM3_CH2, TIM3_CH3, TIM3_CH4 — exactly the
table order. Two independent structures agree.

These are the **default** alternate-function pins for those timers. **No `AFIO_MAPR` write exists
in the image** — the single `AFIO` constant is only reused as a base to reach `GPIOA`
(`AFIO + 0x800`). Two consequences: no remapping to account for, and **SWD is never disabled**,
so you keep debug access.

Every one of these eight pins is broken out on a Blue Pill, and none collide with USB
(PA11/PA12) or the LED (PC13).

## 3. Timing — matches the datasheet

`RCC_APB1ENR` gets TIM2EN|TIM3EN|TIM4EN; `RCC_APB2ENR` gets IOPAEN|IOPBEN (GPIOA, GPIOB only).

All three timers share one time base:

```
TIM_Prescaler = 2        -> divide by 3
TIM_Period    = 59999    -> 60000 counts
72 MHz / 3 / 60000       =  400 Hz
```

The constant `72000000` appears at file offset `0x33D0`, so the firmware expects a **72 MHz
SYSCLK** — i.e. the standard 8 MHz HSE × 9 PLL that a Blue Pill already has. Output-compare mode
is `0x60` (PWM mode 1) with preload enabled on all eight channels.

## 4. UARTs — RESOLVED

Read from the live chip (BRR, while PX4 was actively probing). `baud = f_clk / BRR`:

| USART | Pins | BRR | f_clk | Baud | Role |
|---|---|---|---|---|---|
| USART1 | PA9 / PA10 | `0x138` (312) | 72 MHz (APB2) | 230,769 ~ **230400** | debug console |
| **USART2** | **PA2 / PA3** | `0x027` (39) | 36 MHz (APB1) | 923,077 ~ **921600** | **host link** |
| USART3 | PB10 / PB11 | `0x168` (360) | 36 MHz (APB1) | **100,000** | S.Bus |

`VOXL2_IO_BAUD` on the VOXL 2 side is **921600**, which matches USART2 uniquely.

Corroborated by GPIO state: before wiring, PA2/PA3 read `4` (floating input). Once J18 was
connected and PX4 began probing, `GPIOA_CRL = bb447bbb` — **PA2 = `B`**, alternate-function
push-pull, i.e. USART2_TX. `GPIOA_CRH = 888447b4` shows PA9 = `B` too, but that is the 230400
console, which will never answer a 921600 protocol packet.

> Wiring to PA9/PA10 looks plausible and fails silently — the driver just reports
> `Board version info response timeout`. Use **PA2/PA3**.

S.Bus (USART3) needs a hardware inverter a Blue Pill lacks. Irrelevant here: RC arrives on ELRS
to VOXL 2 J19 directly, and the driver is started with `-e` (external RC).

## 5. Wiring

Host side is **VOXL 2 J18** (DSP UART QUP2 = port 2), JST-GH 4-pin, 3.3 V logic. Port 7 stays
with the CRSF receiver on J19, so there is no conflict. Note the TX/RX crossing:

| J4 pin | Signal | Blue Pill |
|---|---|---|
| 1 | 3.3 V from host | `3V3` **directly** — bypass the regulator, do not also feed 5 V |
| 2 | RX from host (host TX) | **PA3** — USART2 RX |
| 3 | TX to host (host RX) | **PA2** — USART2 TX |
| 4 | GND | `G` |

PWM outputs are 3.3 V logic, which essentially every PWM ESC accepts. Never power an ESC or servo
from the board's 5 V pin — on the real M0065 that pin is a reference/monitor only.

## 8. The board on this bench is a clone

Measured over SWD:

| Register | Value | Meaning |
|---|---|---|
| DAP IDCODE | `0x2BA01477` | genuine STM32F1 reports `0x1BA01477` |
| DBGMCU_IDCODE | `0x20030410` | DEV_ID `0x410`, REV_ID `0x2003` — plausible, and what clones fake |
| Flash size reg | **128 KB** | a real C8 reports 64 |
| Unique ID | `1a5a5bb5-00000000-01f34a24` | middle word all zeros; ST encodes lot/wafer data there |

Not ST silicon — consistent with a CKS32/GD32-class part. **It works fine here**: the firmware only
uses TIM2/3/4, GPIOA/GPIOB and a USART, all register-compatible, and it boots and configures
correctly. Two practical consequences:

- `target/stm32f1x.cfg` refuses to attach on the IDCODE mismatch. Override it:
  `-c "set CPUTAPID 0x2ba01477"` before sourcing the target config (`m0065-flash.sh` does this;
  set `TAPID=...` to override again).
- `stm32f1x mass_erase` **times out** on this part. Not needed — `program` erases the sectors it
  writes.

If anything misbehaves later, suspect the clone first.

## 9. WORKING — the 16 MHz crystal problem and its one-byte fix

The M0065 uses a **16 MHz crystal**; a Blue Pill has **8 MHz**. The firmware sets
`PLLXTPRE` (HSE/2) x9, expecting 16 MHz -> 72 MHz. On 8 MHz that gives **36 MHz — everything at
half speed**: USART2 at 461538 instead of 921600, PWM at 200 Hz instead of 400 Hz.

Symptom: the driver reports `Board version info response timeout` forever. Captured over DMA, the
board received `49 68 fe` repeated three times (PX4's three retries) instead of an `0xAF` packet —
the classic 2x baud garble.

**Fix — patch one byte** (or fit a 16 MHz crystal):

```
0x08004f7a:  f443 13f8   orr.w r3, r3, #0x1f0000   <- PLLSRC|PLLXTPRE|PLLMUL9
0x08004f7a:  f443 13e8   orr.w r3, r3, #0x1d0000   <- PLLXTPRE cleared
```

That is file offset **0x337C**, `f8` -> `e8`. Verified after flashing: `RCC_CFGR = 0x001d040a`,
SYSCLK 72 MHz, PCLK1 36 MHz, USART2 923077 baud.

Detection then succeeds:

```
Board Type : 35: ModalAi I/O Expander (M0065)
Unique ID  : 0x01F34A24000000001A5A5BB5     <- matches the SWD-read clone UID
Firmware   : version    2, hash f94baad1
Bootloader : version    0, hash              <- empty; the driver does NOT care
Reply time : 520us
Driver initialization succeeded
```

The missing ModalAI bootloader is a non-issue: only id / HW version / FW version are validated.

### Verifying PWM output

**Do not read `TIMx_CCRn` — it reads 0.** The firmware uses one-pulse mode and reloads the compare
register per pulse. Sample `GPIOx_IDR` statistically instead: at 400 Hz a 1000 us pulse reads high
~40 % of the time, 1900 us ~76 %.

```bash
adb shell 'px4-actuator_test set -m 1 -v 0.8 -t 15'
```

Measured, with `VOXL2_IO_MIN=1100 MAX=2000` (so value v -> 1100 + 900v us):

| Motor | Channel | Pin | Commanded | Expected | Measured |
|---|---|---|---|---|---|
| 1 | 1 | PA0 | 0.8 | 1820 us / 72.8 % | 74 % |
| 2 | 2 | PA1 | 0.9 | 1910 us / 76.4 % | 75.5 % |
| 3 | 5 | PA6 | 0.95 | 1955 us / 78.2 % | 78 % |
| 4 | 4 | PB9 | 0.9 | 1910 us / 76.4 % | 74 % |

### Channel 3 / PB8 is dead on this particular board

PB8 never outputs, at any commanded value, while PB9 on the same timer works. Firmware config is
identical for both (`TIM4_CCER=0x1100` with CC3E and CC4E set, `CCMR2=0x6868` both PWM1). Driven
as a plain GPIO push-pull the pin does reach logic high, but **configured as input-with-pull-up it
reads 0** — something external pulls PB8 down on this board. Moving Motor 3 to channel 5 works
perfectly, which proves the driver and protocol are fine.

**Working config — skip channel 3:**

```bash
adb shell 'px4-param set VOXL2_IO_FUNC1 101; px4-param set VOXL2_IO_FUNC2 102; \
           px4-param set VOXL2_IO_FUNC3 0;   px4-param set VOXL2_IO_FUNC4 104; \
           px4-param set VOXL2_IO_FUNC5 103; px4-param save'
```

Motors 1-4 -> **PA0, PA1, PA6, PB9**. Check PB8 for a solder bridge before trusting it.

## 7. Safety

This drives motors. A wrong pin or prescaler means uncommanded spin-up.

- **Props off** for the entire bring-up.
- Bench supply with a **current limit**, not the 6S pack.
- Confirm all eight pins on a scope or logic analyser **before any motor is connected**.
- Motors restrained before the first powered test.

## Reproducing the analysis

```bash
adb pull /usr/share/modalai/voxl2-io-tools/firmware/modalai_m0065_firmware_v0_2_RC1_f94baad1.bin m0065.bin
arm-none-eabi-objdump -D -b binary -m arm -M force-thumb --adjust-vma=0x08005000 m0065.bin > m0065.asm
```

Note `--adjust-vma`, not `--adjusted-vma`, on this binutils. The GPIO tables are raw data at file
offsets `0x3FB0` and `0x3FD0`; read them with a hex dump rather than the disassembler, which
renders them as bogus instructions.
